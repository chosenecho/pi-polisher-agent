# 视频转录文稿书面化风格（Transcript）

## 风格目标
将视频、播客、访谈或课程的语音转录逐字稿转化为干净、通顺、自然易读的书面文本；在消除口语杂音与转录瑕疵的同时，最大限度保留讲述人原有的思考脉络、论述顺序与细节信息，不做摘要式删减或主观改写。

## 改写细则
1. **清除口语杂音与转录瑕疵**：
   - 删除无实义的填充词、语气词和口头禅（如“嗯”“呃”“那个”“就是说”“对吧”“怎么说呢”“其实呢”）。
   - 合并口语中的结巴、无意义重复和自我纠错（如“上周三，不对，是上周四”直接整理为“上周四”），保留讲述人最终确认的正确表达。
   - 结合上下文修正明显的语音识别（ASR）同音错别字与错误断词。
2. **口语彻底转化为书面文本**：
   - 将明显的口语词、俗语和随口表述替换为规范、准确的书面词汇（例如：“翻车”→“失效/出现问题”、“乱七八糟”→“复杂多变/不规范”、“互相打架”→“相互冲突”、“抽风”→“出现异常”、“搞定”→“解决/完成”、“塞了一堆”→“堆砌了大量”）。
   - 补全口语中省略的主语、连接成分与准确标点，并按语义自然分段；将松散的口播开场与互动语（如“大家好啊，今天我想跟大家聊一下”“大家可以看到屏幕这里”）转化为自然的书面引入或过渡，但不得丢失其引出的实质内容。
   - 保持平实、流畅、有条理的书面文本感，做到“读起来像精心撰写的文章”，而不是“去掉语气词的逐字稿”；同时避免生硬官腔或空洞套话。
3. **最大限度保留原始逻辑与顺序**：
   - 严格沿用原文的讲述顺序、推演链条（因果、转折、递进、对比、举例、前提与结论），**严禁擅自重排段落或论点顺序**。
   - **严禁做摘要式压缩**：保留原文中的具体案例、数据、限定条件和必要铺垫，不删减有效论据，也不额外编造原文未提及的观点或总结。
4. **理顺流水长句与隐含衔接**：
   - 将口语中一连串“然后……然后……就是……”的流水账长句，按原本的语义关系拆分为清晰连贯的书面句，用准确的逻辑连接词（如“因此”“不过”“比如”“接着”）替代泛化的“然后/就是”。
   - 保留原讲述人的人称视角（如“我”“我们”），确保读者的视角和原作者一致。

## 参考示例
- 原文：嗯就是说，我们做这个架构改造的时候，一开始其实大家都觉得，哎呀直接换个数据库不就行了吗，对吧？然后我们就去压测了一下，结果发现根本不是数据库的问题，是因为那个缓存击穿，不对，是缓存雪崩，然后导致所有的请求一下子全打到后端去了，所以我们后来就先把热点数据做了多级缓存，再去慢慢拆库。
- 润色：在进行架构改造之初，团队原本认为直接更换数据库即可解决问题。但在压测后发现，瓶颈并不在数据库本身，而是缓存雪崩导致大量请求瞬间涌向后端。因此，我们决定先为热点数据引入多级缓存，随后再逐步推进分库工作。

- 原文：那接下来呢我想聊第二个点，就是很多人写提示词的时候，他会习惯把所有的规则全塞到一段话里面，然后模型就很容易漏掉中间的约束，比如你既要它控制字数，又要它保持某种语气，然后还要它输出JSON，它经常顾此失彼，所以我的经验是把角色定义和具体风格拆开来管理，这样后面你调哪一块都不会互相打架。
- 润色：接下来讨论第二点。许多人在编写提示词时习惯将所有规则堆砌在同一段文本中，这很容易导致模型遗漏中间的约束条件。例如，当同时要求模型控制字数、保持特定语气并输出 JSON 格式时，它往往会顾此失彼。因此，我的经验是将角色定义与具体风格拆分管理，这样后续调整任意模块时都不会相互干扰。
